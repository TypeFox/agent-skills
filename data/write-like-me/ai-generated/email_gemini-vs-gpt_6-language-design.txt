On the DSL structure, I’d take a middle path between fully monolithic and fully modular.

For the PoC, I agree with Marcus that we should keep the **document itself single-file**. That keeps the editing model, JSON generation, and AI context straightforward.

At the same time, I would still design the language so that **named reusable definitions and cross-references are possible inside that file**.

Conceptually, something like:

```
sensorProfile highSpeedOpti {
    model OptiTrack-X
    frequency 1000Hz
}

system sorterA {
    sensor left  uses highSpeedOpti
    sensor right uses highSpeedOpti
}
```

rather than repeating the complete sensor configuration every time.

There are a few reasons I like this structure.

First, it maps better to how users tend to think about repeated hardware configurations: define a meaningful concept once, then use it where needed.

Second, it gives the LLM shorter and more stable structures to generate. Instead of recreating a long parameter block several times and potentially introducing subtle differences, it can define a valid profile once and reference it.

Third, we don’t lose much simplicity. Langium handles references naturally, so we can resolve them and validate the resulting configuration before generating the legacy JSON. The JSON generator can still expand everything into the exact monolithic structure your flashing tooling expects.

I would **not** introduce multiple files, imports, packages, or a sophisticated module system during the PoC. That would add lifecycle and resolution questions we simply don’t need yet.

So my recommendation is:

**PoC authoring:** one DSL file
**Language model:** supports named reusable concepts and references
**Generated output:** fully expanded legacy JSON
**Future option:** multi-file modularization if real-world projects eventually justify it

One important point is that we shouldn’t introduce references just because the language technology supports them. Joachim can start with the first Nexus-Core examples in a mostly direct form, and we’ll add a reusable definition as soon as we encounter genuine repetition in the factory examples.
