Hi Alex,

This is perfect timing, because we’re at exactly the point where we should be deliberate about context rather than gradually accumulating a giant prompt.

My recommendation is: **use all three sources you mentioned, but give each one a very specific job.** We definitely should not dump the raw grammar, complete hardware catalog, validation rules, and example library into every request.

Joachim will structure the AI context in layers.

**1. Language descriptor: teach the model what the DSL is**

We’ll use Langium AI to derive a compact descriptor from the actual Langium project and generate our baseline system prompt from that.

That gives the model an accurate description of the language constructs, relationships, and syntax without treating the raw `.langium` grammar as documentation. The grammar remains the source of truth, but we translate it into something optimized for the model.

This is important because the descriptor evolves with the DSL. If we change the profile syntax next week, we don’t want a manually maintained prompt quietly drifting away from the executable language.

**2. Curated domain guide: teach it what the hardware means**

This is where a short Markdown document is extremely valuable.

I’d ask Marcus to prepare something concise rather than comprehensive—probably a few pages at most—covering:

* Nexus-Core, OptiTrack, and DriveServo concepts and terminology
* the important relationships between them
* defaults that matter semantically
* the major topology restrictions
* the small set of rules where a human engineer would say, “You need to know this before configuring the system”

What we don’t need is a prose transcription of every parameter and every validation rule. Those facts already exist in deterministic structures in the application.

For larger catalogs later, I’d rather retrieve the relevant hardware information for the current task than permanently load the whole catalog into the prompt.

**3. Few-shot examples: show it what good configurations look like**

We should absolutely use some of your `known-valid` DSL examples, but selectively.

Three or four carefully chosen examples will probably teach the model more than twenty near-duplicates. I’d choose examples that demonstrate different concepts:

* a basic Nexus-Core configuration
* profiles and repeated references
* a configuration involving DriveServo
* the high-speed sorting scenario or something close to it

The examples should show idiomatic DSL, not merely syntactically valid DSL. We want the assistant to learn the style we would actually like customers to produce.

Then there is a fourth layer that I think is the most important:

**4. Dynamic context: give the model only what matters right now**

For each interaction, Joachim can add the relevant state from the application:

* the current DSL document or selected section
* referenced profiles
* relevant effective/default values from our normalized model
* current Langium diagnostics
* hardware facts needed for this particular request

So if the user asks why an OptiTrack sensor cannot run at a certain frequency, we don’t need to remind the model about every DriveServo parameter.

And during repair, the feedback becomes even narrower: here is the candidate configuration, here are the deterministic diagnostics, fix those issues without changing unrelated parts.

That gives us a context pipeline roughly like:

**Langium descriptor + compact domain guide + a few canonical examples + task-specific state**

followed by:

**generate → parse → validate → feed diagnostics back → repair → validate again**

The last part is critical. We shouldn’t put pressure on the prompt to make hallucination impossible—that’s an unrealistic standard for an LLM. We should make the first attempt good, then let the deterministic language infrastructure catch whatever remains.

There’s one more thing I’d like to add to Week 4: **evals from day one.**

We already have excellent raw material. Your two target workflows, `known-valid` examples, invalid configurations, power constraints, profile expansion, and the high-speed sorting case can become a small evaluation suite.

That lets us answer questions empirically:

* Does adding a particular domain rule to the prompt improve success?
* Are three examples better than one?
* Does the assistant correctly reuse profiles?
* How often does generation pass validation on the first attempt?
* When it fails, how reliably does the repair loop converge?
* Does a prompt change fix one scenario while degrading another?

I’d much rather tune the context against those results than debate the perfect system prompt by intuition.

So for Marcus: **yes, please prepare the Markdown domain guide**, but keep it intentionally compact. Think “what an experienced Vanguard engineer would explain to a new engineer in their first hour,” not “complete hardware reference manual.”

Joachim can take care of deriving the language description and selecting the initial few-shot examples from the DSL corpus. We’ll then refine all three against the eval results.
